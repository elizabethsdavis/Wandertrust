## HARD CONSTRAINTS (do not skip)
- The app is **live with real Firestore data**. **No change to the persisted data shape without a backward-compatible migration + fallback.** There is no schema version and no read-time normalizer, so every field name in the state blob is a frozen contract.
- Persisted shape (from the DB audit):
  - `state/{uid}` = `{ state: "<JSON string>", updatedAt }`. The parsed string holds the `usePersist` keys: `trips[]`, `wardrobe{}`, `customOccasions[]`, `otdItems[]`, `catalogTemplate|null`, `wardrobeMeta{}` (UX batch; `{ [itemName]: { color?, brand?, colorName?, type? } }` — `color` / `brand` are manual corrections that win over parsing, absent = parse the name; `colorName` / `type` (Fields batch, additive) are what was typed into the separate colour / type fields, kept for prefilling and never read by the parser), `categoryMeta{}` (rename batch; `{ [categoryId]: { label?, icon? } }` — display overrides for a category's name / emoji, resolved by `src/lib/categories.js`; `{}` = defaults), `addins|null` (Home Screen batch; `{ types: { [tripTypeId]: { [section]: [item] } }, weather: { [tempBandId|"rain"|"snow"]: { [section]: [item] } } }`, item = `{ name, e?, ff?, needsRefill?, needsCharge?, needsWash? }`; null = the built-in `COND_ITEMS` for trip types and no weather add-ins — see `src/lib/addins.js`), `savedOutfits[]` (Outfits batch; the closet: `{ id, name, slots, photo|null, createdAt, updatedAt, source? }` — `slots` = `{ [slotId]: string | string[] }` with the same nine frozen slot ids and the same empty-string / array convention as an occasion's `slots`; `photo` = `{ url?, path?, cardUrl?, cardPath?, thumb?, dataUrl? }` — cloud mode stores the Storage download URL + object path of the full image, the same for its ~480 px card rendition (`cardUrl` / `cardPath`, Photo Quality fix, additive — absent on photos saved before it), and a ~80 px JPEG data-URL thumb (~2 KB); local mode a 320 px `dataUrl` + thumb; **never a full image in the doc**; `source` = `{ tripId, trip, day, occasion }` for outfits imported from a past trip; see `src/lib/outfits.js`).
    - `trip` = `{ id, destination, tripType[], days, weather, startDate, tempRange, items[], otdItems[], otdChecked{index:bool}, createdAt, icon, weatherData, conditions?[], outfitIds?[] }` — `outfitIds` (Outfits batch, additive) = the saved outfits shortlisted for this trip ("what I'm bringing"); each occasion in `outfitPlan[d][i]` may carry `outfitId` (the saved outfit it wears) and `customized` (its `slots` were tweaked after assignment) — additive, and an occasion **always keeps its own `slots` copy**, so the packing sync, the Tops/Bottoms migration and older builds read exactly what they always read; deleting a saved outfit only removes the link. — `conditions` (Home Screen batch, additive) holds `"rain"` / `"snow"` as ticked on the wizard's weather step (auto-detected from the forecast text); it only selects weather add-ins at generation time.
    - `item` = `{ id, name, category, section, packed, essential, ff, freq, needsRefill, needsCharge, refilled?, charged?, needsWash?, washed? }`; `category ∈ outfits|activewear|necessities|health|tech|toiletries|checkout`. `needsWash`/`washed` (Laundry mode) and the `health` category are UX-batch additions; `health` is populated by `genList` for new trips and by the load-time migration for old ones (six sections moved out of `necessities`: Hydration, Nutrition, Supplement Stack, Energy: Sleep & Wake, Pain & Sickness, Hygiene & Immune). Outfit-synced items now use sections `Tops` / `Bottoms` / `Shoes` / … instead of one `Clothing` section (migrated using the trip's `outfitPlan`; anything unmatched stays `Clothing`). **Order is the array order of `trip.items`** — Arrange mode just rewrites the array, no position field. Likewise the template's section order is its object-key order and item order its array order (JSON keeps both); the editor's drag-and-drop only rewrites those, and `genList` follows them.
    - `trip.icon` is user-editable since the rename batch (tap the emoji in the trip header) — same field, any single emoji.
    - **Category ids are frozen** (`outfits|activewear|necessities|health|tech|toiletries|checkout`); only their *display* label / emoji can change (`categoryMeta`). Section names in the template can be renamed (object key re-keyed in place; existing trips keep the section names their items carry).
    - template item (`catalogTemplate[cat][section][]`) = `{ name, f, e?, ff?, cond?, needsRefill?, needsCharge?, needsWash? }` — the three flags are UX-batch additions, copied onto generated items by `genList`. `migrateTemplate` moves the six health sections from `necessities` to `health` in a stored template.
  - `users/{uid}` = `{ phone, onboarded, createdAt }`.
  - **Cloud Storage** (Outfits batch): `outfits/{uid}/{outfitId}.jpg` — a ~1200 px JPEG per outfit photo — and, since the Photo Quality fix, `outfits/{uid}/{outfitId}_card.jpg` (~480 px, for the cards); owner-only via `storage.rules`; the state blob only holds their download URLs + paths. Nothing else lives in the bucket.
  - `credentials/{autoId}`, `challenges/{autoId}` — passkeys, server-only.
  - localStorage mirror keys: `pp2_trips|pp2_wardrobe|pp2_customOccasions|pp2_otdItems|pp2_catalogTemplate|pp2_wardrobeMeta|pp2_addins|pp2_categoryMeta|pp2_savedOutfits`, plus `pp2_owner` = the uid the cached data belongs to (since Tier 3; absent for local-mode / pre-cloud data so onboarding can still import it). Helpers live in `src/lib/localMirror.js`.
  - **Migrations (`src/lib/migrations.js`)** run once per load in `PackPal.jsx` after the store is `ready`, are idempotent, and only write when something changed: (1) legacy `checkout` items → `otdItems` (pre-existing), (2) `necessities` items in the six health sections → `category: "health"`, (3) `outfits` items in section `Clothing` → `Tops`/`Bottoms`/… via `slotToSection` + the trip's `outfitPlan`; plus `migrateTemplate` for a stored `catalogTemplate`. A device still on the old build keeps migrated data intact (its category loop skips `health` items until it updates — they stay in the blob and in the counts — and the three-way merge keeps both sides' edits).

### DB-safety (data-layer audit)
- ✅ **P0 — multi-device data loss (Tier 4b):** single JSON blob, loaded once at login, `setDoc` last-write-wins (no `onSnapshot`; `updatedAt` written but never read). Two devices/tabs → last save clobbers the other. Inherent to the single-blob design; needs an `onSnapshot` listener and/or conflict detection to fix.
  - **How it works now (`src/lib/store.jsx` + `src/lib/merge.js`):** after the initial load the store subscribes with `onSnapshot`; `baseRef` holds the cloud `state` string this device last applied or wrote (the merge ancestor — the string itself is the version, so **no new Firestore fields**). A remote change is applied wholesale when this device is clean, or three-way merged (`mergeState(base, local, remote)`) when it holds unsaved edits, then pushed. Writes go through `runTransaction`: the doc is re-read inside the transaction and merged onto if it moved since `base` (Firestore re-runs the function on contention). Merge rules: unchanged side yields; both changed → by identity (trip id, item id, slot, OTD name, per-index `otdChecked`, saved outfit id); same field changed on both → local wins; a deletion sticks unless the other side edited that record. Own writes are recognised via `pendingJsonRef`. Account shows \"Updated from another device HH:MM\".
  - Still true: everything is one document, so two devices editing at the *exact* same moment converge via merge rather than being both kept as separate versions — for a packing list that is the right trade-off.
  - Also shipped in Tier 4a (related): a failed write is now visible (amber dot, \"Not synced\" + **Retry** in Account) and auto-retried on the browser `online` event; sign-out flushes first. What's still missing is the *read* side: a second device never learns about writes made elsewhere until it reloads.
- ✅ **P1 — 1 MiB doc limit (Tier 4a):** `pushCloud` measures the serialized blob (`TextEncoder`) before every write; over `CLOUD_DOC_LIMIT − 8 KiB` it refuses the write, sets `syncState = "full"` (red dot, Account explains with real KB numbers and that deleting old trips frees space). `useStoreMeta()` exposes `sizeBytes`/`sizeLimit`; Account shows a storage line from 50% up. Still not pruned: `weatherData` per trip remains the biggest item — a future improvement is to drop `weatherData.forecast` beyond the trip window (that IS a data-shape change → migration).
- ✅ **P1 — empty-blob clobber path (Tier 4a):** on load, a missing cloud doc for a uid whose mirror is on this device (`pp2_owner === uid`, non-empty) is treated as "cloud doc gone" — the mirror is kept, flagged `error`, marked dirty and re-uploaded on the next flush/edit — instead of an empty new account that would push `{}` over the old data.
- **Confirmed additive/non-breaking:** `catalogTemplate` (except the `KNOWN_KEYS` gap, B2) and the collapse feature (pure UI, nothing persisted).

Elizabeth's ask: *the ×, edit and card tappable space are getting convoluted; one horizontal carousel is getting gnarly as I add more tops — think through the best way to easily pick the right one.* Chosen in chat: vertical list + search + chips; ⋯ at the row's end for edit / remove; keep the auto-jump to the next slot after a pick.

| # | What | Behaviour | Where |
|---|------|-----------|-------|
| 1 | **Rows, not cards** | Each piece is a full-width row: swatch dot, name, a small line with the brand, the pattern and where / when it was last worn ("Kyoto · Travel Day · 2 days ago"), a check when picked. **Tap the row = pick** (single slots still jump to the next slot after 350 ms; multi slots toggle). The **⋯** at the row's end (44 px, its own border) opens *Edit piece*; *Remove from wardrobe* is the trash button in that sheet (hidden for the current pick). No × on rows any more. | `components/WardrobePicker.jsx` (`Row`) |
| 2 | **Find it fast** | A search field ("Find a top… colour, brand or type") filters as you type — every word must match the name, brand, pattern or colour family; Enter with exactly one match picks it. Chips under it: **All**, one per colour family present (dot + name + count, largest first), then one per brand (count). A chip shows that family / brand flat; search and chips combine. Nothing matches → "No tops match “…”" and **Add “…” as a new top**, which opens the add form with the query carved into colour / brand / type (`splitItemName`) and the focus on the type. The `+` beside the search opens the empty form; with an empty wardrobe the old dashed "Add new top" button shows instead. | `WardrobePicker.jsx`, `OutfitEditor.jsx` (`openAddForm`, `NewPieceForm initial`) |
| 3 | **Recently worn + colour groups** | With 6+ pieces the list is sectioned: **Recently worn** (up to 4, newest first — dates come from the saved outfits' `updatedAt` and the trips' `startDate` / `createdAt` that wear the piece), then one group per colour family ("Black · 3", largest first, "Other" last, A→Z inside). Under 6 pieces: one flat list, most recently worn first. Filtering always shows a flat list. | `lib/pieces.js` (`pieceIndex`, `pieceFacets`, `filterPieces`, `groupPieces`), `PackPal.jsx` (`pieceIndexFor`) → `OutfitBuilder` / `Closet` → `OutfitEditor` (`pickerIndex`) |
| 4 | **Reachable navigation** | The ‹ / Next / Done bar at the bottom of the editor is `position: sticky`, so it stays on screen under a long wardrobe; the add form renders *above* the list for the same reason. | `OutfitEditor.jsx` |
| 5 | **Verification** | Node: 17 checks on the index (uses counted case-insensitively, latest use wins, trip start date vs outfit updatedAt), facets, filters (words, pattern, secondary colour, chips), grouping (threshold, order, Other last). Browser harness WP1–WP5 on a seeded 9-piece wardrobe: sections + counts + "where worn", no × and one ⋯ per row, search (brand word, every-word, no-match → prefilled add form, cancel restores), colour and brand chips, All, tap-to-pick + auto-advance + pressed state, ⋯ → sheet (no remove for the current pick), sticky bar, save. Every older check passes unchanged apart from the swatch helper reading `[data-piece]` / `[data-swatch]`. 174/174; cloud 47/47. | `scripts/browser-checks.py` |

Not built on purpose (say the word): a "Manage" / multi-select mode for bulk removal; sorting choices (the order is fixed: recent, then colour); remembering a search or chip between slots; photos per piece (only outfits have photos).

Manual check worth one pass on the phone: open an outfit → Top → type two letters in the search → tap a chip → tap a row (it jumps to Bottoms) → back on Top the row is highlighted; tap ⋯ → the sheet; scroll a long list → Next stays put.

## Git note
This repo pushes through a per-repo alias because the machine has two GitHub accounts + an `insteadOf` SSH rewrite. Use **`git pushpp`** (defined in `.git/config`) to push as `elizabethsdavis` from her own Terminal. Plain `git push` fails with "denied to elizabeth-davis-dd," and the Cowork VM cannot push at all.

**The way batches actually ship is the GitHub web uploader — see `GITHUB_UPLOAD.md`** (bundle via `python3 scripts/upload-plan.py "<Batch name>"`, upload folder by folder in the listed order, one commit per upload in the format `<Verb-first summary> - <Batch name> N/M`, then verify and `git reset --hard origin/main`). Note `pushpp` pushes to a URL, so `origin/main` is NOT updated by it; run `git fetch origin` to refresh the ahead/behind count.
